# ZITADEL Kubernetes Auth IdP Plan

## Goal

Add ZITADEL as a Kubernetes-only reference auth IdP in parallel with Authentik,
with full parity where ZITADEL supports the same behavior. The reference should
exercise opaque ZITADEL access tokens through RFC 7662 introspection and avoid
resource-owner password grants, which ZITADEL does not support.

## Scope

- Add `contrib/auth/zitadel` with a provider manifest, README, Kubernetes docs,
  and an umbrella Helm chart.
- Keep the NeMo Platform runtime integration provider-neutral by using OIDC
  configuration, introspection, and a standard `groups` claim.
- Use ZITADEL-generated client IDs and secrets. A Helm seed job will create the
  ZITADEL demo project, OIDC app, machine users, role grants, and custom groups
  action, then patch the local NeMo Platform ConfigMap with generated values.
- Keep Docker Compose out of scope for now.

## Implementation Steps

1. Add the ZITADEL provider manifest and schema support for non-password token
   grants.
2. Add the ZITADEL umbrella Helm chart with ZITADEL, NeMo Platform, Envoy,
   workload-token signing key, workload-token TLS, and TokenReview RBAC.
3. Add a post-install/post-upgrade seed job that uses the ZITADEL FirstInstance
   admin PAT, stores generated demo credentials in `nemo-zitadel-seed-state`,
   patches `nemo-platform-config`, and restarts the NeMo API/controller pods.
4. Update auth-idp test helpers to support `client_secret_basic` and opaque
   token claim resolution through introspection.
5. Make the Kubernetes runtime helper provider-aware so Authentik and ZITADEL
   can share the same live contract harness.
6. Add static tests for the manifest, Helm chart, seed job, Envoy routes,
   introspection config, workload-token secrets, and TokenReview RBAC.
7. Update auth integration docs and provider README files.

## Known ZITADEL Differences

- No resource-owner password credential grant. Contract tests use generated
  machine-user `client_credentials` grants for setup and workload-provider
  tokens.
- ZITADEL opaque access tokens are not locally decodable JWTs. Runtime tests
  must read claims from introspection when local JWT decoding returns no claims.
- ZITADEL client IDs and secrets are generated by the IdP. The local chart uses
  placeholders and patches generated values after seeding.
